## Motivation

> “The best way to learn is to learn in public.”

I came across 'learning in public' mindset with the [blog post](https://www.swyx.io/learn-in-public) by Shawn Wang. The idea stronly resonated with me, after spending many years attending lectures, consuming online tutorials, and reading research papers without redistributing the knowledge somehow. 

So I wanted to start sharing what I learned and built as an ML practitioner as a way to enrich my learning experience and to contribute my insights to the vast community of knowledge.

Starting this blog felt similar to launching a small product — imperfect but public. And I'm excited to build upon it.

## Results

I built a technical blog that could serve as my portfolio and platform for sharing my learnings and experiences, using Hugo and GitHub Pages.

[Hugo](https://gohugo.io/) is an open-source static site generator written in Go. Instead of relying on a database or server-side logic, Hugo compiles your posts and layouts into plain HTML, CSS, and JavaScript files, resulting in very quick build times. 

[GitHub Pages](https://docs.github.com/ko/pages) is a free hosting service provided by GitHub that allows you to publish static websites directly from a repository. By pushing your site files (or the output generated by tools like Hugo) to a designated branch, you can automatically deploy and update a live website without managing servers or infrastructure. 

This combination offered the following advantages:
- speed & performance: static sites are faster than WordPress setups, for example.
- free hosting
- security & maintenance: static site has fewer vulnerabilities (e.g. no plugin updates, no database attacks), which means it's lower maintenance
- customization & flexibility: customizable layouts with HTML/CSS, hugo themes are easy to switch

The most appealing point for me was that this set up enabled developer-friendly workflow in my blog. After writing my posts in Markdown, I used Git for version control and deployed with CI/CD logic by pushing my post for automatic site update. Blogging felt like software development process, which I'm familiar with. Overall, it was a great option for my blog with a lightweight, customisable workflow to showcase my projects. 

## Implementation 

I followed the [guide](https://carpentries-incubator.github.io/blogging-with-hugo-and-github-pages/index.html) by the carpentries incubator to set up the blog with Hugo and GitHub Pages. In this blog post, I only went over the implementation conceptually, so you can check out the specific steps and codes in the abovementioned guide.

The implementation consists of three big steps: creating a Hugo project locally, configuring a GitHub repository for deployment, and building static files which could be automatically published by GitHub Pages. 

1. Create and preview the site locally

After a GitHub repository for the blog is set up, the site can be created locally with Hugo.
Hugo provides a project scaffold that separates content, layout, and configuration into a clear folder structure, as shown below. Blog posts are written as Markdown files under the ```content/``` directory and themes for visual representation of the blog can be downloaded as a Git Submodule in the ```themes/``` directory. During development, Hugo’s built-in preview server (```hugo server```) allows changes to be rendered instantly in the browser(```http://localhost:1313```), making it easy to iterate on content and design before deployment.

```
my-project/
├── archetypes/
│   └── default.md
├── assets/
├── content/
├── data/
├── i18n/
├── layouts/
├── static/
├── themes/
└── hugo.toml         <-- project configuration
```
Source: https://gohugo.io/getting-started/directory-structure/

2. Configure deployment

After pushing the local Hugo site to Github repository, the project is connected to a GitHub repository and configured for GitHub Pages hosting via ```hugo.toml``` and ```cd.yml``` files. Project configuration file, ```hugo.toml```, includes metadata of the site, such as theme and baseURL. In ```hugo.toml```, it is important to set the correct ```baseURL```, which determines how links and static assets are resolved once the site is deployed. GitHub Action workflows are YAML files that contain triggers, jobs and steps that are detected and performed automatically. As such, in ```cd.yml```, the deployment workflow is set up, including choosing the branch that will trigger the build process, ensuring that updates to the source files automatically result in an updated public website. The example code snippet is shown below. After the configurations are pushed to the repository, GitHub Action workflows can be further configured at the repository with branch protection rules and required status checks, etc. 

```
name: Build and Deploy Site

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

jobs:
  build-and-deploy-site:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repo
        uses: actions/checkout@v2
        with:
          submodules: true
          fetch-depth: 0

      - name: Setup Hugo
        uses: peaceiris/actions-hugo@v2
        with:
          hugo-version: 'latest'

      - name: Build site with Hugo
        run: hugo --minify

      - name: Check HTML
        uses: chabad360/htmlproofer@master
        with:
          directory: "./public"
          arguments: --only-4xx --check-favicon --check-html --assume-extension --empty-alt-ignore --disable-external
        continue-on-error: true

      - name: Deploy to GitHub Pages
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./public
```

3. Build and publish

Unlike dynamic web frameworks, Hugo generates a complete static website during the build step. Running the build command produces a set of HTML, CSS, and JavaScript files in the ```public/``` directory, representing the final version of the site. But in this setup, since GitHub Actions handle Hugo build step, GitHub Pages does not serve Hugo source files, which means the ```public/``` folder does not need to be committed to a GitHub repository. A new blog post can be generated as a Markdown file and once the changes are pushed to the repository, GitHub Pages serve the site without requiring server-side infrastructure.


## Reflection

The implementation steps reminded me of ML process, as in:
- Step 1 is about preparing the experiment environment
- Step 2 is about configuring the training/deployment pipeline
- Step 3 is about running the pipeline and releasing results

Setting up the blog also taught me several practical lessons:
First, details matter in deployment configuration process. Small mistakes like incorrect base URL may break a site after deployment, even when that works locally. Deployment environments can be case-sensitive, which means I had to pay attention to file extensions as well — an image file named .JPG loaded locally but not on GitHub Pages until I renamed it to .jpg. 

Second, static site deployment with GitHub Actions workflow resembles a typical CI/CD pipeline. I initially expected to commit Hugo’s generated public/ folder to the repository in order to publish the site. However, the GitHub Actions workflow automatically builds the static site during deployment and uploads the generated files to GitHub Pages. This means the repository only needs to contain the source content and configuration, while the build artefacts are created dynamically. I was able to understand this separation with hands-on experience.
